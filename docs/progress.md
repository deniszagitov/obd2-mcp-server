# Сохранённый прогресс CT200h MCP

17 ноября 2026. Ветка `codex/ct200h-readonly-diagnostics`, версия `0.1.1.dev0`.
База upstream: `03d351e7cc33c0985ca816716273804d9bb24bfc`.

## Код и защита

Работа сосредоточена на чтении диагностики через существующий BLE ELM327.
Драйвер, профиль OBDb, декодеры, тесты и документация находятся в этом репозитории.
Сервер работает только в read-only: явный флаг `--read-only` и безопасное
поведение по умолчанию. Переключения в write-режим через CLI/MCP нет.

Стирание DTC скрыто из списка инструментов и отклоняется до подключения,
в том числе с `confirm=true`. Оба реальных драйвера запрещают стирание.
Serial проверяет каждый запрос перед передачей python-OBD; BLE использует
фиксированный allowlist. Произвольные команды, инъекции строк, coding,
security access и actuator tests не предоставляются.

Read-only допускает необходимые временные настройки ELM и передачу
диагностических запросов чтения. Это защита интерфейса этого MCP, а не
ограничение других программ с самостоятельным доступом к устройству.

## Подтверждённый охват

* 57 ECU/PID записей стандартного Mode 01, из них 56 декодированных и 1 raw.
* Попытка всех 215 применимых OEM-запросов: 44 полных ответа, 2 неполных,
  31 отрицательный ответ выбранного ЭБУ, 138 ответов без нужного responder.
* 228 полей из полных OEM-ответов с маркировкой `decoded_unverified`.
  Формулы/единицы требуют независимого подтверждения для этой калибровки.
* Стандартные `03/07/0A`, `02`, `06`, `09` с discovery и пагинацией.
  Engine Mode 06 вернул 17 записей по 9 MID. Недоступные данные сохраняют
  статус ошибки; из них не выводится отсутствие неисправностей.
* Строгий ISO-TP, bounded NRC78, журнал BLE chunks, межпроцессный владелец
  адаптера и отдельные статусы транспорта/декодирования.

Более подробное поведение: [диагностика и ограничения](ct200h-readonly-diagnostics.md).

## Проверки

142 теста проходят, включая запрет прямого/устаревшего action-вызова,
защиту перед подключением, serial/BLE guards, инъекции, неполные сообщения,
порядок кадров, изоляцию ECU, pending response и безопасный partial-prefix.
У новых файлов проверки Ruff проходят; прежние замечания upstream остаются.

`scripts/verify_read_only_mcp.py` проверяет установленный сервер настоящим
stdio MCP-клиентом: handshake с версией, список инструментов, offline-каталог
BLE и отказ в стирании только в отдельном mock-процессе. Машина не подключается.
Локальные протоколы проверки сохраняются в `local/validation/`.

Текущую версию в Codex проверять по ответу самого MCP, а не по факту установки:
`get_server_status` либо поле `server` любого JSON-ответа. Ожидаются
`version=0.1.1.dev0`, `read_only=true`, `source_matches_disk=true` и совпадение
`loaded_source_sha256` с установленным кодом. Статус устаревшего процесса
не пересчитывает его загруженную версию из новых файлов.

На момент сохранения установленный `0.1.1.dev0` проверен, конфигурация Codex
явно включает `--read-only`. После пользовательского Restart ответ активного
чата всё ещё не содержал нового поля `server`, а новые процессы с флагом не
появились. Поэтому актуальность **активного соединения Codex пока не подтверждена**;
после полного перезапуска приложения необходим повторный запрос статуса.

## Полный локальный архив

`local/progress/session-2026-11-16.tar.gz` содержит **полные** прежние `outputs/`
и `work/`: hardware-захваты, измерения, трассы, все экспериментальные скрипты,
исследованные исходники, старые патчи, сборки и протоколы проверок. Содержимое
каждого обычного файла проверено побайтно; SHA-256 и размеры перечислены в
`local/progress/manifest.json`. Исходное рабочее место также сохранено.

`local/` исключён из Git: это личные данные машины, старые конфигурации и
идентификаторы устройства, которые не должны попасть в будущий upstream PR.
Переносимые код, исследования и тесты сохранены в Git. Архив нужно копировать
отдельно при переносе всей локальной работы на другой компьютер.
