# Lexus CT200h: полнота чтения через ELM327 и Car Scanner

Проверено 16 ноября 2026 года. Исследование первичных документов и исходных данных; аппаратные запросы в этой части не выполнялись.

## Вывод

11 значений, возвращённых прежним `get_live_data`, нельзя считать пределом автомобиля или ELM327. Для получения большего набора серверу нужны обнаружение стандартных PID и профиль расширенных запросов Lexus/Toyota с адресами блоков, сборкой многофреймовых ответов и формулами. Полное совпадение с конкретной конфигурацией Car Scanner без её профиля/фактически полученных значений пока не установлено.

## Что умеет Car Scanner

В [описании приложения от разработчика в App Store](https://apps.apple.com/us/app/car-scanner-elm-obd2/id1259933623) заявлены расширенные PID, freeze frame и Mode 06. [История базы профилей разработчика](https://www.carscanner.info/profile-database-changelog/) содержит Toyota Prius Gen.3 и Lexus/Toyota ~2010–2022 CAN + extra sensors. Это объясняет возможное различие с generic OBD-клиентом; точный профиль пользователя неизвестен.

[Официальное описание custom PID](https://www.carscanner.info/custompids/) определяет три необходимые части: команда (service/mode + PID), ECU header и формула. Одна ECU-команда может возвращать несколько полей. Буква A в формуле означает первый байт полезных данных после удаления заголовков, длины, positive service response и PID. Также приложение поддерживает вычисляемые показатели и action PID; последние могут запускать действия и не нужны серверу чтения.

Надпись `ELM327 v2.1` не удостоверяет набор возможностей. Разработчик Car Scanner отдельно предупреждает, что строку версии подделывают, а реальные ограничения могут касаться адресов ECU, AT-команд и длины ответов. То, что конкретный показатель уже читался тем же адаптером на iPhone, — гораздо более полезная проверка совместимости. [Выбор адаптера, первичный источник](https://www.carscanner.info/choosing-obdii-adapter/)

## Как расширять чтение

Стандартные PID обнаруживаются битовыми картами `0100`, `0120`, `0140` и последующими страницами по continuation bit. [Документация python-OBD](https://python-obd.readthedocs.io/en/latest/Command%20Tables/) прямо перечисляет `PIDS_A/B/C`; [её исходный код](https://github.com/brendan-w/python-OBD/blob/master/obd/obd.py) загружает supported commands по полученным картам. Это больше фиксированного списка из 11 датчиков, но всё ещё не универсальный каталог расширенных данных всех блоков.

[Официальный ELM327 datasheet](https://www.elmelectronics.com/wp-content/uploads/2016/07/ELM327DS.pdf), разделы OBD Commands, Multiline Responses и Altering Flow Control Messages, описывает функциональный CAN header `7DF`, физический `7E0 → 7E8`, ответы нескольких ECU, `ATH1`, `ATSH` и flow control. На примере запроса `0100` показано, как выяснять отвечающие адреса. Поэтому фильтр только `7E8` скрывает другие блоки. Для крупных расширенных ответов необходима корректная ISO-TP-сборка с проверкой ECU, заявленной длины и sequence number. Длинный ответ нельзя трактовать как набор отдельных однобайтовых датчиков.

## Источники расширенных определений и их ограничения

Актуальная [база OBDb Lexus CT200h](https://github.com/OBDb/Lexus-CT-200h/blob/d5067c8578d05b0e224df19232798caa660a11b9/signalsets/v3/default.json) содержит **221 команду и 650 определений полей** (подсчитано из live GitHub/raw, commit `d5067c8578d05b0e224df19232798caa660a11b9`). Это каталог кандидатов, а не 650 прочитанных значений. Есть debug-пометки, охват разных лет, неоднородные единицы и дополнительные поля за пределами 14 блоков. Файл распространяется по CC BY-SA 4.0; перенос должен сохранять атрибуцию и условия лицензии.

В таблице ниже A, B… — байты уже собранного payload после удаления service/PID; `U16(X,Y)=256*X+Y`. Формулы OBDb приведены для проверки, а не как доказанная калибровка автомобиля пользователя.

| Кандидат запроса | Показатель/формула | Уровень подтверждения |
|---|---|---|
| `7E2 → 7EA`, `015B` | SOC, `A*100/255` % | [Производитель ScanGauge, Prius GenIII 2010–2015](https://www.scangauge.com/support/x-gauge-commands/prius/); совместимость CT2013 проверить |
| `7E2 → 7EA`, `2187` | Воздух батареи и TB1–TB3; OBDb: четыре U16-поля, `raw*0.0039047837-50` °C | ScanGauge подтверждает семейство запроса температуры для Prius GenIII; конкретную раскладку проверить |
| `7E2 → 7EA`, `2181` | Напряжения блоков; первые 14 пар U16, `raw*0.0012205692` В | OBDb-кандидат; не переносить дополнительные поля автоматически |
| `7E2 → 7EA`, `2192` | Min/max блоков и номера | OBDb-кандидат |
| `7E2 → 7EA`, `2195` | Внутренние сопротивления, `byte/1000` Ом | OBDb-кандидат; количество полей проверять |
| `7E2 → 7EA`, `2198` | Ток `(U16(A,B)-32768)/100` A; также SOC-поля и ограничения мощности | OBDb-кандидат; SOC at ignition on не переименовывать в текущий SOC |
| `7E2 → 7EA`, `2174/2175` | Температуры DC/DC и охлаждающей жидкости инвертора | Производитель ScanGauge, Prius GenIII; совместимость CT2013 проверить |

[ScanGauge публикует эти запросы отдельно для поколений Prius](https://www.scangauge.com/support/x-gauge-commands/prius/): GenII SOC через `7E3/21CE` нельзя автоматически применять к GenIII/CT. Ещё один первичный открытый проект [PriusCAN](https://github.com/gyimesibalazs/priuscan/blob/main/DEVELOPER_GUIDE.md) использует engine `7E0`, hybrid `7E2`, A/C `7C4`, ABS `7B0`; это подтверждает подход к адресации для GenIII, но не гарантирует идентичность CT.

У OBDb запросы `2181/2187/2192/2195/2198` имеют `dbgfilter {to:2015,from:2017}`. По структуре опубликованных year-support данных это объединение внешних диапазонов, оставляющее 2016 вне debug, а CT2013 — требующим проверки. Сама JSON Schema не формализует union, поэтому это отмечено как вывод из использования данных, а не цитата стандарта.

Для проверки декодера есть архивированные ответы настоящих CT2016: [2181, многофреймовые напряжения](https://github.com/OBDb/Lexus-CT-200h/blob/d5067c8578d05b0e224df19232798caa660a11b9/tests/test_cases/2016/commands/7E2.7EA.2181.yaml), [2187, температуры](https://github.com/OBDb/Lexus-CT-200h/blob/d5067c8578d05b0e224df19232798caa660a11b9/tests/test_cases/2016/commands/7E2.7EA.2187.yaml), [2161, положительные и отрицательные обороты MG1](https://github.com/OBDb/Lexus-CT-200h/blob/d5067c8578d05b0e224df19232798caa660a11b9/tests/test_cases/2016/commands/7E2.7EA.2161.yaml). Они содержат raw response и expected values; это полезнее синтетического теста, повторяющего реализацию. В том же репозитории есть CT2011 `2101/2121/2168`; fixtures для 2013 года при проверке не найдены. Replay проверяет соответствие источнику и целостность транспорта, а не исправность автомобиля или точность всех названий базы.

## Декодер и честное обозначение покрытия

[Первичная спецификация OBDb](https://github.com/OBDb/.schemas/blob/main/signals.json) и [документация её автора](https://pelican.clutch.engineering/handbook/obd/extended-pids/format) задают `bix`, `len`, `sign`, `blsb`, `mul/div/add`. `sign:true` означает signed raw; scaled value вычисляется после извлечения. `nullmin/nullmax` — включительные пороги null. Пример `len:16, div:10, nullmax:6553` показывает применение порога к scaled value. Документация Pelican описывает clamp min/max; для диагностического сервера целесообразно сохранить исходное значение и отметить out-of-range, чтобы не замаскировать ошибку смещения/формулы.

Рекомендуемая реализация: отдельный каталог с source/version/ECU/service/PID/unit/статусом проверки; отделить advertised support, successful read, no data, timeout, negative response и decode error. Каждый замер должен содержать время, блок-источник и контекст. Чтения группировать по ECU-команде и ограничивать частоту. Доступные для чтения Mode 01/21/22 запросы отделять от сброса ошибок, кодирования, active tests и произвольных start/stop diagnostic commands. READY нужен достоверно описанный бит/показатель: RPM=0 либо 14 В сами по себе его не доказывают.

## Сопоставление с iPhone

[Официальная инструкция записи](https://www.carscanner.info/records/) позволяет экспортировать запись в CSV или BRC. На iOS: Data recording → свайп записи влево → More → Share → CSV. Запись содержит отображавшиеся числовые параметры, их зависимости и некоторые поля общего ответа; текстовые значения не записываются. Поэтому CSV полезен для сверки названий, единиц и динамики, но не является полным списком поддерживаемых PID и не обязан содержать ECU/команды/формулы. BRC — внутренний формат Car Scanner. Точный актуальный публично документированный способ экспорта встроенной базы профиля/всех raw ECU-транзакций не установлен.

Для окончательного сравнения нужны название выбранного профиля и список фактически работающих датчиков Car Scanner (запись CSV помогает). Без этого можно расширить сервер и измерить его покрытие, но нельзя честно заявить полное совпадение с телефоном.
