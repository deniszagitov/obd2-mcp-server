# Сравнение OBD MCP upstream для Lexus CT200h

Проверено 16 ноября 2026 года: текущие default branches GitHub, исходники, тесты, issues/PR, releases/tags. Ссылки на код зафиксированы на SHA. Никаких аппаратных запросов, fork/push/issue/PR в этой исследовательской части не выполнялось. Полные тестовые наборы upstream не запускались; выполнена одна изолированная проверка с fake connection без аппаратуры.

**Вывод:** ни один из трёх проектов не даёт полного покрытия возможностей ELM327 или всех блоков CT200h. Для уже работающего локального Python/BLE сервера самый короткий путь — сохранить базу petrpatek, выделить универсальные исправления в небольшие PR, профиль CT200h держать отдельно. Если строить новый универсальный продукт с несколькими драйверами, наиболее развитая архитектурная основа — ayhammouda; переход на неё потребует существенной разработки BLE, Mode 21 и групповых декодеров. Shoka полезнее как образец стандартных диагностических чтений и обработки неизвестных значений, но переход на TypeScript сам по себе не расширяет доступ к автомобилю.

## Найденные конкретные проблемы

1. **Petrpatek serial: обход подтверждения очистки через live read.** `get_live_data(pids)` применяет `getattr(obd.commands, supplied_name)` и вызывает `query` без проверки режима. Передача `CLEAR_DTC` достигает Mode 04, обходя `_handle_clear_dtc` с `confirm`. Проверено локально на fake connection, без constructor и аппаратуры: fake зарегистрировал команду `CLEAR_DTC`. [Точный путь: obd_connection.py:146–152](https://github.com/petrpatek/obd2-mcp-server/blob/03d351e7cc33c0985ca816716273804d9bb24bfc/src/obd2_mcp/obd_connection.py#L146-L152), [отдельное подтверждение: server.py:381–389](https://github.com/petrpatek/obd2-mcp-server/blob/03d351e7cc33c0985ca816716273804d9bb24bfc/src/obd2_mcp/server.py#L381-L389). BLE фиксированная карта этим конкретным обходом не затронута.
2. **Petrpatek: no-data превращается в «ошибок нет».** BLE возвращает `[]` на bus error/пустой ответ, serial — на null response; handler сообщает clean/all scanned modules. Это не доказанный чистый результат. [BLE:907–911](https://github.com/petrpatek/obd2-mcp-server/blob/03d351e7cc33c0985ca816716273804d9bb24bfc/src/obd2_mcp/ble_connection.py#L907-L911), [handler:348–360](https://github.com/petrpatek/obd2-mcp-server/blob/03d351e7cc33c0985ca816716273804d9bb24bfc/src/obd2_mcp/server.py#L348-L360).
3. **Petrpatek BLE: ошибки CAN DTC framing и смешения ответов.** `get_dtcs` сразу разбирает пары после `43`, не убирая CAN count byte; extractor не проверяет declared ISO-TP length/sequence и может склеивать ответы разных ECU. Например, payload `43 01 04 20` не должен декодироваться парами с первого `01`. Это статический вывод из [907–964](https://github.com/petrpatek/obd2-mcp-server/blob/03d351e7cc33c0985ca816716273804d9bb24bfc/src/obd2_mcp/ble_connection.py#L907-L964); аппаратно не проверялось.
4. **Petrpatek BLE initialization меняет persistent adapter PP.** Без отдельной настройки вызывает `ATPP 0E SV 00` и `ATPP 0E ON` как best effort. Это не запись в ECU, но изменение адаптера не следует прятать в обычное чтение. [672–718](https://github.com/petrpatek/obd2-mcp-server/blob/03d351e7cc33c0985ca816716273804d9bb24bfc/src/obd2_mcp/ble_connection.py#L672-L718).
5. **Ayhammouda DTC unavailable различается недостаточно явно.** Внутри hardware driver `response.value is None` становится пустым tuple; слой не возвращает отдельный no-data status. По одной такой пустоте нельзя заключать, что DTC отсутствуют. [elm327.py:383–395](https://github.com/ayhammouda/obd-mcp-server/blob/d317182138804af555214321bb57e9ec7139abfc/src/obd_mcp/drivers/elm327.py#L383-L395). Это ограничение достоверности, не найденный write-policy bypass.

У shoka исследованный normal tool path использует фиксированную карту PID, а clear требует env opt-in + confirm + отдельную MCP elicitation. Обход, аналогичный petrpatek, здесь не найден. Это не полноценный security audit. Политику нельзя считать аппаратным ограничителем: экспортируемый низкоуровневый код и доверенные plugins по-прежнему выполняются с правами процесса.

| Generic declared-profile loader/decoder | Самостоятельный PR после transport/parser | Несколько decoded fields на один response, источники/version/year/debug scopes, bounded reads. Не добавлять arbitrary AT/ECU command passthrough. |
| 650 OBDb CT definitions и реальная конфигурация конкретной машины | Отдельный data package/локальный профиль | [OBDb CT dataset](https://github.com/OBDb/Lexus-CT-200h/blob/d5067c8578d05b0e224df19232798caa660a11b9/signalsets/v3/default.json) — CC-BY-SA-4.0, не часть MIT-кода. Нужны pin, attribution/license, изменения и provenance; не переобозначать как MIT. Каталог не означает 650 живых чтений. |
| Адаптация в ayhammouda | Только если выбран долгосрочный migration | Потребуются normalized BLE driver, policy/schema для Mode 21, multi-signal response groups и расширение standard reads; перенос текущего CT файла не заработает сам. |

В ayhammouda [ProfileReadDefinition](https://github.com/ayhammouda/obd-mcp-server/blob/d317182138804af555214321bb57e9ec7139abfc/src/obd_mcp/profiles.py#L182-L220) описывает один `signal_id` и decoder, а [валидация:242–248](https://github.com/ayhammouda/obd-mcp-server/blob/d317182138804af555214321bb57e9ec7139abfc/src/obd_mcp/profiles.py#L242-L248) запрещает повтор ECU/service/identifier. Поэтому 14 значений блока батареи в одном `2181` не помещаются в текущую модель без расширения. Это важнее числа инструментов MCP.

Если отправлять вклад в ayhammouda, его [CONTRIBUTING:56–85](https://github.com/ayhammouda/obd-mcp-server/blob/d317182138804af555214321bb57e9ec7139abfc/CONTRIBUTING.md#L56-L85) требует provenance, разрешение на данные и DCO sign-off; реальные captures/logs в PR не принимаются. Для generic core использовать самостоятельные synthetic fixtures. У petrpatek PR приветствуются, но срок реакции maintainer неизвестен. Публичный fork полезен как воспроизводимый источник локальной версии; монолитный PR со всей CT конфигурацией затруднит review.

## Чего «использование ELM327 по максимуму» не доказывает

ELM327 предоставляет транспорт и AT-настройки, но не универсальную базу всех датчиков автомобиля. Нужны ответы конкретных ECU, правильные service/PID, формулы и проверенные состояния автомобиля. [Официальный datasheet](https://www.elmelectronics.com/wp-content/uploads/2016/07/ELM327DS.pdf) описывает функциональную/физическую адресацию и многофреймовые ответы; он не обещает полный Lexus-каталог.

Отсутствие значения может означать неподдерживаемый PID, неактивный блок, состояние зажигания, timeout, ограничение адаптера, неподходящую адресацию или дефект декодера. Полноту полезнее показывать по слоям: стандартные advertised PID → успешно читаемые standard PID → проверенные enhanced commands/fields → ещё не проверенные definitions → неподдержанные read services. Mode 02/06/07/09/0A и manufacturer reads — разные категории информации; добавление их не равнозначно включению всех ELM AT-команд или управляющих процедур.
