# Что взять из awesome-canbus для OBD2 MCP

Дата проверки: 16 ноября 2026. Контекст: Python MCP, macOS, BLE ELM327, Lexus CT200h с локальным предположением о модельном годе 2013. Это исследование документации и исходников; совместимость с нашей машиной и реальные подключения не проверялись.

Список проверен по [awesome-canbus, снимок `0afb838`](https://github.com/iDoka/awesome-canbus/blob/0afb8381a1ec573f3cb386a4176fb92be315a0e2/README.md). Все основные проекты ниже присутствуют в списке; **opendbc — дополнительный смежный источник**, связанный с panda/cabana.

## Что уже есть у нас

Оценка опирается на текущие файлы рабочего каталога, включая существующие незакоммиченные изменения; это не проверка установленного MCP-процесса или автомобиля.

- BLE ELM327 подключается через Bleak. На границе отправки действует фиксированный список разрешённых команд, отдельно сериализованы команды и выбор ECU с последующим чтением. Источник: `src/obd2_mcp/ble_connection.py`, `READ_ONLY_COMMANDS`, `_send_command`, `_sensor_session`.
- Уже сохраняются текстовые ответы запросов и статусы ошибок. `_trace_command` дополнительно умеет собирать границы BLE notifications, ASCII/hex, время, prompt и результат записи. Однако `capture_trace` по умолчанию выключен; в просмотренных CLI/MCP-инструментах нет записи полного сеанса в файл. Источник: тот же файл, `__init__`, `_on_notify`, `_trace_command`, `_query_sensor`; `src/obd2_mcp/server.py`, `parse_args`, `TOOLS`.
- Есть собственная сборка ISO-TP, проверка ECU/длины/последовательности и каталог OBDb. 650 полей каталога не означают 650 доступных датчиков. Специальная адресация `eax`/`fcm1` в текущем транспорте не поддерживается. Источник: `src/obd2_mcp/diagnostics.py`, `can_message`, `extended_catalogue`.
- Уже существуют replay fixtures OBDb и проверки BLE fragments, таймаутов и неполных ответов. Для `7EA/2181` предусмотрен узкий экспериментальный случай 34 из 35 байт с явным `allow_partial_prefix`; по умолчанию такой ответ отклоняется. Это поведение кода и синтетических тестов, не установленная причина проблемы реального адаптера. Источники: `tests/test_sensor_discovery.py`, `tests/test_ble_transactions.py`, `tests/test_partial_prefix.py`.

Таким образом, ближайший пробел — сохраняемый и переносимый сеанс с повторяемыми сценариями и удобными графиками. В исходном наборе зависимостей (`pyproject.toml`) пока нет `python-can`, `cantools` или UDS/ISO-TP библиотек; пассивный raw CAN backend в просмотренном коде отсутствует.

## Приоритеты

Моя оценка: наибольшую ближайшую пользу дадут воспроизводимые проверки диалога с адаптером и анализ сохранённых измерений. Полноценный CAN backend имеет смысл отдельным этапом: библиотека для CAN сама по себе не превращает BLE ELM327 в надёжный высокоскоростной CAN-регистратор.

| Приоритет | Проект | Как использовать с нашим сервером | Что потребуется |
|---|---|---|---|
| 1 | [elmulator](https://github.com/qadanm/elmulator) | Воспроизводить разбиение BLE-ответов, паузы, пропавший prompt, обрыв соединения | Преобразование наших трасс в сценарии; адаптация тестового транспорта |
| 1 | [PlotJuggler](https://github.com/PlotJuggler/PlotJuggler) | Смотреть графики уже расшифрованных OBD-показаний и сравнивать записи | Экспорт измерений в CSV; проверка выбранной сборки на Mac |
| 2 | [ELM327-emulator](https://github.com/Ircama/ELM327-emulator) | Отдельный multi-ECU стенд для serial/python-OBD и тестов диагностических ответов | Собственный CT200h-сценарий; это не готовый mock Bleak |
| 2 | [python-can](https://github.com/hardbyte/python-can) | Импорт CAN-логов, виртуальная шина, будущий transport для USB-CAN/SocketCAN | Отдельный raw CAN backend; выбор совместимого с macOS драйвера |
| 2 | [cantools/cantools](https://github.com/cantools/cantools) | Превращать кадры CAN в именованные сигналы по DBC; декодировать сохранённые логи | Проверенный DBC для конкретного автомобиля |
| 2 | [SavvyCAN](https://github.com/collin80/SavvyCAN) | Визуально изучать raw CAN-логи, проверять гипотезы о сигналах | Экспорт или импорт настоящих CAN-кадров; совместимое железо для live capture |
| 3 | [python-can-isotp](https://github.com/pylessard/python-can-isotp) | ISO-TP для нового CAN backend; источник проверочных случаев сегментации | Доступ к отдельным CAN-кадрам, ответственность за flow control |
| 3 | [python-udsoncan](https://github.com/pylessard/python-udsoncan) | Типизированный UDS-клиент для подтверждённых ECU/DID | Описания DID и рабочий транспорт; не готовая база Toyota PID |
| 3 | [can-utils](https://github.com/linux-can/can-utils) + [can327/elmcan](https://github.com/norly/elmcan) | Linux-стенд: захват, виртуальная шина, ISO-TP диагностика | Linux и подходящий интерфейс; BLE GATT не равнозначен TTY |
| 3 | [panda](https://github.com/commaai/panda) + [opendbc](https://github.com/commaai/opendbc) | Отдельное направление для raw CAN и сверки Toyota/Lexus сигналов | Дополнительное железо и проверка покрытия CT200h 2013 |

Таблица — инженерная рекомендация. Проверенные возможности и оговорки приведены ниже.

## 1. elmulator: наиболее подходящий кандидат для BLE-регрессий

Проект описывает общий JSON-сценарий для Python/Swift TCP, Swift BLE peripheral и встроенного Swift BLE test double. Можно задать части ASCII-ответа, задержку, зависание и обрыв соединения. Для реального BLE peripheral на macOS настраиваются service/write/notify UUID, размер notification и искусственное разбиение потока. Лицензия MIT. [README](https://github.com/qadanm/elmulator), [сценарии](https://github.com/qadanm/elmulator/blob/48971d5115a530f3ddf311d083a3c02ee0953a24/SPEC.md), [настройка BLE](https://github.com/qadanm/elmulator/blob/48971d5115a530f3ddf311d083a3c02ee0953a24/docs/getting-started.md).

**Предлагаемая интеграция:** переводить сохранённый диалог нашего адаптера в сценарии и прогонять одинаковые ответы с разными границами chunks, задержкой и reconnect. Отдельно проверять, что поздний фрагмент старой команды не становится новым показанием, а неправильная длина/ECU/последовательность кадров не получает статус успешного измерения.

**Ограничения:** встроенный BLE test double реализован для Swift/CoreBluetooth и не подменяет Python Bleak напрямую. Python TCP требует тестового TCP-транспорта; live BLE peripheral требует проверки соединения и наших GATT UUID. Сценарий может воспроизвести наблюдённый дефект, но не доказывает причину дефекта или исправление реального адаптера. Формат сценария задаёт задержку перед первой частью ответа; точное воспроизведение всех промежутков между уведомлениями следует проверить отдельно. [Спецификация семантики ответа](https://github.com/qadanm/elmulator/blob/48971d5115a530f3ddf311d083a3c02ee0953a24/SPEC.md).

Проект новый: GitHub указывает создание 5 июля 2026 и последнюю отправку изменений 15 ноября 2026; поэтому сначала стоит проверить один небольшой сценарий и закрепить версию. [Метаданные проекта](https://api.github.com/repos/qadanm/elmulator).

## 2. PlotJuggler: ближайшее практическое дополнение к нашим показаниям

PlotJuggler загружает CSV, строит временные и XY-графики, позволяет сравнивать записи и вычислять производные ряды. Это подходит для сохранённых OBD-измерений: температуры, тока, SOC, скорости и напряжений блоков батареи, если соответствующие чтения доступны и их формулы проверены. Лицензия MPL-2.0. [README](https://github.com/PlotJuggler/PlotJuggler), [официальный сайт](https://www.plotjuggler.io/).

**Предлагаемая интеграция:** добавить ограниченную по длительности и числу запросов запись выбранных PID и экспорт числовых рядов в CSV. Сохранять индивидуальное время чтения, единицу, ECU и статус достоверности; не превращать `unavailable` в нули и не выдавать последовательные чтения за одновременный снимок. Метаданные и полные ответы держать рядом в JSONL, а для CSV формировать числовые колонки по датчикам с отдельными timestamps и пропусками.

Например, сравнение подтверждённых напряжений блоков с током и SOC может помочь заметить зависимость разброса от нагрузки. Вывод о неисправности требует валидных измерений и диагностических критериев; сама визуализация этого не устанавливает.

**Ограничения:** CSV-экспорт ещё предстоит реализовать. В текущем релизе 4.1.0, по проверенному списку release assets, опубликованы Windows/Linux пакеты; наличие macOS target в проекте не подтверждает готовый подходящий нам установщик. В релизе также указана браузерная версия, но импорт наших данных в неё не проверялся. [Релиз 4.1.0](https://github.com/PlotJuggler/PlotJuggler/releases/tag/4.1.0), [список assets](https://api.github.com/repos/PlotJuggler/PlotJuggler/releases/latest), [сборка из исходников](https://github.com/PlotJuggler/PlotJuggler/blob/main/docs/BUILDING.md).

## 3. ELM327-emulator: готовый стенд диалога с несколькими ECU

Ircama/ELM327-emulator работает на macOS/Linux/Windows, предоставляет serial pseudo-terminal и TCP, поддерживает несколько ECU, диагностические сценарии и ISO-TP flow control. В комплекте есть сценарий Toyota Auris Hybrid; это полезная отправная точка для Toyota-подобного диалога, но не модель нашей CT200h. Bluetooth-вариант использует Classic RFCOMM/SPP. [Официальное описание](https://github.com/Ircama/ELM327-emulator).

**Предлагаемая интеграция:** запуск отдельного процесса для проверки startup, AT-настроек, выборки ECU и реакций на `NO DATA`/отрицательные ответы. Для serial/python-OBD это ближе к реальной границе, чем подмена уже декодированных значений внутри MCP.

**Ограничения:** не проверяет наш Bleak/GATT путь автоматически. В репозитории указана **CC BY-NC-SA 4.0**, поэтому это отдельная тестовая программа с учётом её условий, а не код для безусловного включения в MIT-сервер. [LICENSE](https://github.com/Ircama/ELM327-emulator/blob/master/LICENSE).

## 4. python-can: фундамент для отдельного CAN backend и офлайн-импорта

Библиотека даёт общую модель CAN-сообщений и backend-интерфейсы на Mac/Linux/Windows. Поддерживает читатели/писатели ASC, BLF, CSV, SQLite, can-utils и других форматов. `LogReader` сам не воспроизводит временные интервалы; для этого предусмотрен `MessageSync`. Лицензия LGPL-3.0. [Проект](https://github.com/hardbyte/python-can), [File IO](https://python-can.readthedocs.io/en/stable/file_io.html).

**Предлагаемая интеграция:** сначала `analyze_can_log` как офлайн-функция без доступа к машине, затем отдельный транспорт для raw CAN. `VirtualBus` позволяет проверять обмен кадрами без драйверов на macOS; его экземпляры обмениваются сообщениями внутри одного процесса, и это не эмуляция арбитража/электрики реальной шины. [VirtualBus](https://python-can.readthedocs.io/en/stable/interfaces/virtual.html).

**Ограничения:** поддержка macOS библиотекой не гарантирует поддержку любого USB-адаптера. Backend должен выбираться по конкретному интерфейсу и драйверу; прямой BLE ELM327 backend в просмотренном перечне отсутствует. SocketCAN — отдельный Linux-путь. [Список интерфейсов](https://python-can.readthedocs.io/en/stable/interfaces.html).

## 5. cantools: декодирование CAN, дополнение к OBDb

Нужен именно [cantools/cantools](https://github.com/cantools/cantools): в awesome есть несколько несвязанных проектов с одинаковым именем. Этот Python-проект разбирает DBC/KCD/SYM/ARXML/CDD, декодирует CAN-сообщения и диагностические DID, поддерживает multiplexing и графики сигналов. Лицензия MIT. [Документация проекта](https://github.com/cantools/cantools).

**Предлагаемая интеграция:** `CAN log → cantools + проверенный DBC → именованные значения → MCP`, с сохранением CAN ID, времени, единицы измерения и версии DBC. Полезен и как независимая проверка выбранных CAN-декодеров.

**Ограничения:** текущие OBDb определения описывают диагностический запрос/ответ, а DBC обычно описывает поля CAN-кадров. Следовательно, cantools не является прямой заменой нашего каталога OBDb или произвольных формул Toyota. Библиотека также не обнаруживает неизвестные значения PID сама: нужен проверенный словарь. Это вывод о применимости по документированному интерфейсу декодирования.

## 6. SavvyCAN: визуальный помощник для настоящих CAN-логов

SavvyCAN позволяет захватывать, сохранять и изучать CAN-кадры; для офлайн-анализа адаптер не требуется. Есть импорт candump, CSV и ряда трассовых форматов, графики и анализ сигналов. README упоминает сборку для macOS. Код проекта MIT; зависимости имеют собственные условия. [README](https://github.com/collin80/SavvyCAN).

**Предлагаемая интеграция:** внешняя GUI для ручной сверки raw capture и DBC, затем перенос подтверждённых декодеров/fixtures в MCP. Для уже декодированных OBD-показаний достаточно обычного time-series CSV и инструмента графиков; SavvyCAN раскрывается именно на кадрах CAN.

**Ограничения:** перечень Qt SerialBus/GVRET интерфейсов не подтверждает работу с нашим BLE ELM327. Формат ELM ASCII-транскрипта требует преобразования и не содержит автоматически точные bus timestamps каждого кадра. Указанная в README macOS-совместимость не заменяет проверку конкретной сборки на нашем Mac.

## 7. python-can-isotp: ISO-TP для нового транспорта

Пакет реализует ISO-TP в Python, в том числе через `python-can`, и отдельно оборачивает Linux kernel ISO-TP. User-space API принимает `rxfn/txfn` для **отдельных CAN-сообщений**, поддерживает адресацию и обработку ошибок. Лицензия MIT. [Проект](https://github.com/pylessard/python-can-isotp), [TransportLayer](https://can-isotp.readthedocs.io/en/latest/isotp/implementation.html).

**Предлагаемая интеграция:** backend `python-can → ISO-TP → diagnostic request`, а также проверочные случаи для таймаутов/нарушений последовательности в наших тестах.

**Ограничения:** ELM327 уже управляет частью CAN/ISO-TP и выдаёт текстовый ответ. Нельзя просто подать этот ASCII-поток в `CanStack` или включить второй независимый flow-control поверх ELM. Точная граница зависит от AT-настроек и выбранного адаптера. Для текущего BLE транспорта сначала нужны воспроизводимые трассы и сравнение поведения; это не автоматическая замена его парсера.

## 8. python-udsoncan: полезен для подтверждённых UDS-сервисов

Клиент UDS управляет запросом/ответом, таймаутами и проверками отрицательного, неполного или неожиданного ответа; транспорт подключается через `Connection`. Есть связка с Python ISO-TP. Лицензия MIT. [Client](https://udsoncan.readthedocs.io/en/latest/udsoncan/client.html), [Connections](https://udsoncan.readthedocs.io/en/latest/udsoncan/connection.html), [проект](https://github.com/pylessard/python-udsoncan).

**Предлагаемая интеграция:** применять только для ECU, у которых подтверждены нужный UDS service и DID с известным декодером. Можно перенять разделение transport/protocol/vehicle schema.

**Ограничения:** UDS-стек не поставляет готовую модель всех Toyota-сервисов и параметров CT200h. Добавление библиотеки не подтверждает новые ECU, режимы или формулы, а также не делает существующие запросы Mode 21 автоматически UDS. Общий MCP-интерфейс для произвольной команды не нужен: новые чтения должны оставаться явно разрешёнными на общей границе транспорта.

## 9. can-utils и can327: инструменты для Linux-стенда

`can-utils` содержит `candump` для записи и фильтрации, `canplayer` для воспроизведения и инструменты ISO-TP. Это утилиты Linux SocketCAN. [Официальный README](https://github.com/linux-can/can-utils).

`elmcan` в современном Linux называется `can327`. Драйвер использует TTY line discipline для serial ELM327, переключает режимы адаптера для приближения full-duplex и прямо описан как best effort; пригодность зависит от реализации ELM/клона. [Документация ядра](https://www.kernel.org/doc/html/latest/networking/device_drivers/can/can327.html), [исходный проект](https://github.com/norly/elmcan).

**Предлагаемая интеграция:** Linux/Raspberry Pi стенд с `vcan` и CAN capture для нового backend, регрессий и обмена файлами с macOS.

**Ограничения:** Linux TTY не появляется автоматически у нашего BLE GATT устройства. Драйвер не устраняет ограничения пропускной способности ELM. Воспроизведение записей следует ограничить виртуальной шиной/стендом; офлайн-чтение файла нашим MCP не требует повторной отправки кадров машине.

## 10. panda/opendbc: направление развития, CT200h 2013 не подтверждён

`panda` предоставляет Python API для чтения raw CAN и фигурирует в hardware-разделе awesome. `opendbc` — смежный проект comma с CAN-определениями и кодом Toyota/Lexus; использовать здесь стоит только необходимые схемы чтения. [panda](https://github.com/commaai/panda), [opendbc](https://github.com/commaai/opendbc).

В просмотренном [Toyota values.py, снимок `fef3c62`](https://github.com/commaai/opendbc/blob/fef3c62606862e9e217d2af3e63aa3d453c36ef4/opendbc/car/toyota/values.py) есть `LEXUS_CTH`, документированный для **Lexus CT Hybrid 2017–18 с Lexus Safety System+**. В дереве DBC есть [toyota_prius_2010_pt.dbc](https://github.com/commaai/opendbc/blob/fef3c62606862e9e217d2af3e63aa3d453c36ef4/opendbc/dbc/toyota_prius_2010_pt.dbc). Ни одно из этих обстоятельств не доказывает совместимость всех сигналов с CT200h 2013.

**Предлагаемая интеграция:** сопоставлять отдельные сигналы с сохранёнными логами нашей машины, фиксировать версию схемы и уровень доказательств. Решение о покупке CAN-железа имеет смысл после определения нужных сигналов и доступных шин; прямой выигрыш от покупки для существующего BLE пути пока не установлен.

## Что отложить

- [ECU-simulator](https://github.com/lbenthins/ecu-simulator) прямо помечен автором как больше не поддерживаемый. В инструкциях остались старые Linux kernel ISO-TP и `socketcan_native`; это полезный справочный пример, но слабая основа нового тестового стенда.
- [ELM327SLCAN](https://github.com/qnx425/ELM327SLCAN) использует специальный bootloader и прошивку PIC18F25K80. Это аппаратная переделка определённого типа адаптера, не библиотека, которая добавит SLCAN нашему BLE устройству.
- [can-explorer](https://github.com/Tbruno25/can-explorer) интересен для поиска меняющихся CAN payload и умеет demo через virtual interface. Для текущих расшифрованных OBD-показаний PlotJuggler ближе к задаче; can-explorer становится полезнее после появления raw CAN backend.
- [Scapy](https://scapy.readthedocs.io/en/latest/layers/automotive.html) пригоден как отдельный инструмент разбора CAN/ISO-TP/OBD и проверки тестовых данных. Для ближайших изменений он избыточен; automotive live capture лучше всего поддерживается на Linux и также требует подходящего CAN интерфейса.

## Рекомендуемая последовательность

1. **Запись сеансов поверх имеющейся трассировки.** Добавить явный режим записи JSONL и ограничение размера/длительности. Сохранять запрос, выбранные ECU, BLE chunks, время, raw response, результат декодирования и версию определения. Имена возможных новых инструментов, например `record_session`/`export_session`, здесь только предложения.
2. **Офлайн-воспроизведение и elmulator.** Сначала повторять те же данные без подключения к автомобилю: полный ответ, неверная последовательность, смешанные ECU, неполные 34/35 байт, таймаут и поздний fragment. Тестовый адаптер должен подавать chunks в обработчик уведомлений и моделировать разрывы; подмена готового результата датчика не проверит транспорт. Сценарии elmulator маркируются `synthetic`, происхождение записей следует сохранять отдельно.
3. **CSV и PlotJuggler.** Записывать выбранные доступные показатели за ограниченный интервал и сравнивать графики. Частота ограничена последовательным ELM-опросом; единый точный период для всех датчиков обещать нельзя.
4. **Офлайн raw CAN импорт.** При появлении файлов CAN добавить `python-can + cantools` как необязательные зависимости и анализатор без отправки кадров. Сначала проверить файл/VirtualBus, затем решать вопрос живого транспорта. ELM transcript, расшифрованные измерения и настоящий CAN capture должны иметь разные типы записей: время BLE notification не равно аппаратному timestamp CAN кадра.
5. **Расширение транспорта и диагностики.** Согласовать общий результат для новых backend: сейчас `OBDConnectionProtocol.get_live_data` возвращает список, а BLE `read_snapshot` — более подробную структуру с raw/status/coverage. Источники: `src/obd2_mcp/obd_connection.py`, `src/obd2_mcp/ble_connection.py`, `src/obd2_mcp/server.py`. ISO-TP, UDS и новые ECU добавлять под подтверждённые чтения, сохраняя существующую политику разрешённых команд на каждом новом транспорте.

Исследование не включает установки, изменения runtime-сервера, запросы к автомобилю или подтверждение покрытия конкретного адаптера/машины.
